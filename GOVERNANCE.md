# Governance

Talk2Nature is an early-stage independent initiative founded and maintained by Raviv Yatom. GitHub hosting under Metivity does not establish a separate funding applicant, scientific institution or nonprofit entity. No advisory board or institutional partnership is currently claimed.

## Decisions and review

Use public issues for ordinary proposals and pull requests for reviewable changes. Describe the problem, intended result, sources, limitations and relevant checks. Larger changes should have a scoped proposal before implementation. Raviv currently makes merge and release decisions; contributors can challenge a decision with new evidence in the same thread. Record the reason for acceptance, deferral or rejection. Private security, conduct and participant matters use the routes below instead of public issues.

Scientific summaries distinguish source findings, our interpretation and proposed experiments. Exact review depth and corrections remain visible. A passing software test is not scientific validation. Independent scientific review is still needed; do not mark founder or AI review as independent expert approval. Publication of new empirical claims requires a protocol, appropriate rights and ethics review, documented methods, meaningful evaluation and relevant scientific review.

Access to maintainer roles is not automatic. Repeated useful contributions and demonstrated review judgment can support a public proposal for expanded responsibility. Raviv must explicitly approve access and its scope. There is presently no elected council or delegated release team.

## Continuity and succession

Raviv is the sole maintainer. No deputy or successor is appointed, and no contributor, organization member, funder, or AI tool is presumed to inherit project authority if he is unavailable. This section is a pause-and-handoff procedure; it does not create a second maintainer or transfer ownership of the Metivity repository.

If maintenance pauses, the README and project status should say so, including which public software is still available and which support, releases, reviews, or services have stopped. While no authorized maintainer is available, do not merge changes, issue new releases, open participant-data intake, start hosted research storage, or make commitments on behalf of the project. The public site may continue to serve its last deployed version, but that is not a support or availability guarantee.

A future handoff requires Raviv's explicit approval of the person's role and scope. Grant access through named accounts and the narrowest suitable GitHub organization role; never share a personal password, session, API token, or recovery code. A code reviewer or release helper does not automatically need organization-owner or repository-admin access. GitHub's [repository-role guidance](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization) distinguishes read, triage, write, maintain and admin responsibilities.

Repository access alone never authorizes access to the owner-only backend, Google identity configuration, cloud or database credentials, private recordings, participant details, ignored local files, or funding drafts. Any separate service or data handoff requires its own owner approval, purpose, access review and credential rotation. Do not copy secrets or private data into the public repository to make a handoff easier.

Before changing the maintainer of record, document the current supported release, deployment and recovery procedures; review open security reports and work; and verify the successor can reproduce the public checks from a clean clone. If no successor is available, leave the project clearly marked as paused. Archiving is a separate owner decision: GitHub describes it as making a repository read-only, so assess its effect on contribution and support routes before taking that step ([GitHub archive guidance](https://docs.github.com/en/repositories/archiving-a-github-repository)).

This procedure does not solve the independent conduct-appeal gap. There is still no independent appeals contact or panel; do not imply otherwise or broaden project-managed community spaces until a real, willing person and a workable process are in place.

## What stays open

Original code remains under Apache-2.0 and original public summaries under CC BY 4.0. Do not add restrictions to those licenses while calling the same artifact open source. Safety and data-admission rules govern this project's contributions and services; they do not amend the code license. Contributors retain their copyrights. Record third-party rights separately; publication does not grant permission over other people's recordings, models or papers.

Keep documented exports and reproducible local workflows available. Prefer contributing to compatible existing tools when that solves the problem. Future paid hosting or services must describe what is charged for and preserve the terms of already published work. Any organizational or funding arrangement remains a separate founder decision.

## People, data and accountability

Follow [community conduct](CODE_OF_CONDUCT.md), [security reporting](SECURITY.md) and [contribution rules](CONTRIBUTING.md). Initial animal work is passive. Do not submit sensitive species locations, private speech, credentials or unapproved recordings. Real-data intake remains closed. Future studies need contextual consent, withdrawal handling, provenance and community authority where relevant; “open” is not a default instruction to release every dataset.

Credit contributions in commits, releases and research notes as appropriate. Disclose material conflicts of interest, funding and substantive AI assistance. Public adoption/impact claims must have dated evidence. Response times are not guaranteed; there is no paid support or bounty program. If maintenance pauses, record it in the README and state what is still supported.
